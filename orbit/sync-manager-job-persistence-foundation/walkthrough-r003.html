1 / Overview

Save sync jobs and track run ownership

This change adds storage for Sync Manager jobs and their operation history. It prevents duplicate mappings and two workers claiming the same section, and lets a caller check whether a write succeeded when its response was lost.

No production caller is connected. Synthetic internal callers supply jobs and worker requests. The new repository saves jobs, lookup records and locks in one DynamoDB table, and operation results in a second. Existing API, UI and worker behavior stays unchanged.

Validated at this HEAD. Validation r004 recommends MERGE for this inactive foundation: all 14 criteria pass, with no unresolved Critical, High or Medium findings.

Review focus

Start: syncJobRepository.mjs, especially executeJobOperation and the helpers that build each operation’s writes.

Key decision: save each job change, related lock or lookup changes, and its history event in one transaction.

Check closely: the expected job ID and current worker must still match when DynamoDB commits; an old success must never stand in for current ownership.

Limits: no production dispatch or expired-lock takeover; unusually deep account paths can require more deletion actions than one transaction allows.

2 / System context

The repository owns the storage rules

Callers must authenticate and authorize access before using this API; current tests supply synthetic identities and job data. The repository validates those inputs and decides which records must change together; the DynamoDB client submits requests. This layer does not authenticate users or fetch Canvas/SIS data.

Two new tables

SyncManagerJobs stores current jobs, lookup records and section locks. SyncManagerJobHistory stores operation results and deleted-job records. SAM gives both generated names, on-demand billing, deletion protection and retention on stack deletion/replacement.

Evidence: deploy/lti-sync-manager-template.yaml · SyncManagerJobs / SyncManagerJobHistory

Infrastructure does not activate a workflow

Only history has TTL cleanup. Jobs and locks do not expire automatically. Environment variables expose table names, but this change adds no production caller or IAM policy. Deployment permissions, backup approval and production integration remain separate work.

3 / Runtime walkthrough

Create a job, claim its section, save the result

This path follows the local tests: they create an ACTIVE / QUEUED job, then call the repository as a worker. No scheduler or Canvas synchronization runs here. Each successful operation also saves an event in the same transaction. A lease is the recorded ownership deadline; expiry alone grants no replacement ownership.

  1. Validate the job data

    createSyncJob assigns a UUIDv4 and validates mapping IDs, creator identities, account path, snapshots and state. Canvas IDs remain strings; SIS IDs are trimmed without losing leading zeroes. This step makes no storage call.

    Evidence: src/models/syncJob.mjs · createSyncJob / normalizeSyncJob; spec AC-1, 14

  2. Check the request and any earlier result

    create requires the job, actor, operation ID and occurrence time. Unexpected fields and inconsistent actor/time values are rejected before I/O. The repository then reads the history event for this job and operation. Matching, unexpired input returns the saved result; reused IDs with different input conflict.

    Evidence: src/repositories/syncJobOperations.mjs · normalizeOperation / operationDigest; AC-9, 14

  3. Save all creation records together

    addJobCreationWrites builds conditional inserts for the job, its UUID lookup and each account lookup. executeJobOperation adds the event, checks the whole transaction’s size and sends it. All inserts succeed together; another job with the same section/course/instructor mapping returns already_exists.

    Evidence: src/repositories/syncJobRepository.mjs · addJobCreationWrites / executeJobOperation; AC-2, 11

  4. Load the requested job before claiming it

    The next call supplies the job UUID, worker/run/generation and lease expiry. After checking input and history, getById follows the UUID lookup to the job record. It verifies the stored UUID, physical key, deployment and model. Missing or inconsistent records return missing to the claim caller.

    Evidence: src/repositories/syncJobRepository.mjs · getById / readValidJobRecord; AC-3

  5. Claim the job and lock the section

    addJobClaimWrites requires ACTIVE / QUEUED and the same queued run ID. One transaction sets RUNNING, saves the worker/run/generation and expiry, inserts a section lock only if absent, and records the claim. A competing section claim returns lock_conflict and leaves its job queued.

    Evidence: src/repositories/syncJobRepository.mjs · addJobClaimWrites; AC-4, 5

  6. Extend this worker’s lease

    heartbeat requires the job UUID, run, worker and generation to match both job and lock. It updates both lease-expiry values and records the result together. Neither expiry can move backward. Expiry alone does not remove the lock or allow another worker to claim it.

    Evidence: src/repositories/syncJobRepository.mjs · addLeaseExtensionWrites / jobAndLockMatchOwner; AC-6

  7. Save the outcome and release the lock

    finish validates the matching owner and run times, then sets IDLE for SUCCESS or FAILED for FAILURE. It saves the sanitized summary, clears activeRun, deletes that worker’s lock and appends the event in one transaction. It leaves desired_state untouched, including a concurrent pause.

    Evidence: src/repositories/syncJobRepository.mjs · addRunCompletionWrites; AC-6
When the database may have committed but the response is lost

The client disables automatic SDK transaction retries. For an uncertain result, the repository reads the exact operation event instead of resending the write. A matching unexpired event returns status: 'applied', recovered: true. Missing, expired or unreadable history returns indeterminate: the caller still cannot tell whether the write committed.

checkOperationOutcome(type, input) checks again without writing. The caller keeps the original operation ID, input and timestamps. Use operation type desired when checking a changeDesiredState result. Confirmed contention/capacity failures use bounded retries; business-condition failures and invalid requests are handled separately.

For a recovered claim, ownershipCurrent is true only if the current job and section lock still match that worker. A previously successful claim alone does not allow a worker to start external work.

Evidence: src/repositories/syncJobRepository.mjs · checkOperationOutcome / checkRecordedOperationResult / executeJobOperationEvidence: src/clients/ddbClient.js · transactWriteEvidence: src/utils/errorClassifier.js · classifyDynamoDbTransactionError; AC-9, 12
Pause, deletion and delayed requests

Pause first: a later claim fails. Claim first: pause changes desired state while the worker remains RUNNING and may still finish. Conditions are checked at commit, so a stale preliminary read cannot overwrite another operation’s fields.

Delete: a nonrunning job can be removed together with every lookup record. The same transaction saves a deletion event and a deleted-job record, called FENCE in storage. Running jobs cannot be deleted.

A recreated mapping receives a new UUID. Every mutation checks the requested UUID; delayed requests for the deleted job cannot modify its replacement, even after deletion history expires. There is no lock takeover or recovery worker in this change.

Evidence: src/repositories/syncJobRepository.mjs · addDesiredStateWrite / addJobDeletionWrites; AC-4–8
Account lookups find jobs; the job record supplies authorization data

listJobLocatorsForAccount returns lookup records and a continuation key. loadJobsFromLocators batch-loads the matching jobs with consistent reads, checks their UUID, key and deployment, and excludes missing or inconsistent jobs. Unprocessed keys are retried; exhausted retries throw INCOMPLETE_READ.

authorizationResource(job) selects only the issuer, root account and inclusive account path for the existing authorization policy. Lookup records and display names never grant access. The existing list endpoint is not switched to these methods.

Evidence: src/repositories/syncJobRepository.mjs · listJobLocatorsForAccount / loadJobsFromLocatorsEvidence: src/repositories/syncJobStorage.mjs · readBatch; AC-3, 12
Accepted limitation for unusually deep account paths (SC-001). A path containing 97 accounts needs 100 transaction items to create a job, but 101 to delete it because deletion also saves a FENCE record. Each operation checks its own complete budget; it never splits the write. The user accepted this unusual case without a creation-time guard.
4 / Data model and contracts

What each stored record means

Caller’s job and operation → validated IDs, state and summary → derived database keys and input hash → job changes plus history → applied result, conflict or indeterminate outcome

Object Meaning, source and owner Identifiers and rules
Job record One Canvas issuer/section/SIS course/instructor mapping. Caller supplies facts; the model validates them and the repository owns writes. This record is the source of truth for the new storage API; code calls it the canonical job. Public job_id: UUIDv4. Physical key: SECTION#section / MAP#course#instructor, in deployment-isolated tables. Desired ACTIVE/PAUSED is separate from execution IDLE/QUEUED/RUNNING/FAILED.
Creator and account data Creation-time facts supplied by a verified caller, persisted on the job. creatorSubject and creatorCanvasUserId are distinct identities. Names are captured display text. Creator name/time are both populated or both null. Account path includes root through direct account. These fields cannot be changed by the repository’s mutation methods; course moves require recreation.
Lookup records
locators in code		 Derived UUID/account entries pointing to a job. The repository creates and removes them with the job; a read must verify the referenced job. JOB_ID#uuid / LOCATOR and ACCOUNT#account / JOB_ID#uuid. Contain job_id and canonicalKey; never used alone to authorize access.
Active run and section lock The current worker’s ownership, recorded by a claim on both job and lock. The queued run ID comes from the caller’s job; claim adds worker, generation and lease. Match job UUID + runId + workerId + generation. Lock key: SECTION#section / LOCK. No TTL cleanup or takeover after expiry.
Operation event and deletion record Repository-generated history of a committed operation. Includes input hash, actor or owner, transition and bounded result. Deletion also writes FENCE for the old UUID. JOB_ID#uuid / EVENT#base64url(operationId) or FENCE. Reads accept records only until their original 180-day expiry (rounded to seconds). History API exposes reads, with no independent edit/delete method.
lastRun Latest completed run’s summary, supplied by the owner and sanitized by the model. Saved on the job and in its finish event. Run ID, times, SUCCESS/FAILURE, nullable observed counts and safe error classification/text. Null count means unknown. Free-form upstream error text is replaced by a fixed description.

Encoding, expiry and information kept out of history

Canvas IDs stay positive decimal strings, including values too large for safe JavaScript integers. SIS IDs lose surrounding whitespace but retain leading zeroes. operationId is a caller-supplied string used as-is, then reversibly encoded as UTF-8/base64url for the key. Events sort by that encoded ID, not by occurrence time.

A SHA-256 hash of normalized operation input and type detects changed-input reuse, including changed timestamps. Application times are integer Unix milliseconds; expires_at is the original occurrence time plus 180 days, rounded up to seconds. Reads ignore expired records even before DynamoDB physically removes them. A retry does not extend retention.

History excludes full job/mapping, creator-name and account/display snapshots. It retains actor or worker identities for internal use; it is not anonymous telemetry. It excludes raw upstream error payloads.

Evidence: src/repositories/syncJobOperations.mjs · operationDigest / createOperationEventEvidence: src/repositories/syncJobHistoryRepository.mjs · getOperation / getFence / query; AC-9, 10
Field types and stored shapes

All jobs: string UUID job_id; string mapping/deployment IDs; string creator subject and Canvas user ID; inclusive string account path; integer millisecond capture/creation times; creator/display snapshots; desired and execution states; nullable activeRun and lastRun. Fields are closed: extra or missing fields fail validation. State is supplied by the caller, not silently defaulted.

Queued run: {runId, queuedAt}. Running run: adds workerId, generation, startedAt, leaseExpiresAt. Generation is a positive safe integer. Lock: keys plus job_id, runId, workerId, generation, leaseExpiresAt.

Event: keys plus job_id, operationId, operationType, inputDigest, occurredAt, expires_at, actor, owner, transition, result. Deletion record: keys plus job_id, operationId, occurredAt, expires_at. Events retain the operation result, not a copy of the whole job.
